# Hub product analytics: archive-before-delete runbook

`scripts/archive_product_analytics.py` is the retention job for `hub_product_events` and `hub_product_engagements`. The backend also exposes a protected synchronous trigger for a bounded run; neither it nor the separate reconciliation job is scheduled automatically.

## Protected HTTP trigger and scheduler

`POST /internal/product-analytics/archive/run` requires `X-Analytics-Archive-Token` to match the dedicated `PRODUCT_ANALYTICS_ARCHIVE_TRIGGER_TOKEN`. A missing or shorter-than-32-character configured token disables the endpoint (503); a missing or incorrect supplied token is rejected (401). Generate a long random secret, give it only to the backend and the scheduler, use HTTPS and never expose it to browsers. This token is separate from the Agent sync token. The endpoint is absent from the public API schema and does not accept a database, environment, retention period or batch size from the caller.

The endpoint runs synchronously and returns **after** the job returns: 200 with `status=completed` or `disabled`, 409 when a batch lock is held, and 503 on failure or configuration errors. One call runs at most one 100-row deleted-resource cleanup batch and one 100-row archive batch **per analytics table**. The response includes aggregate cleanup and archive counts plus `has_more`: a full batch sets it to true because more work may remain; an additional call checks. A false value describes the completed run, not concurrent new arrivals. Existing database locks are per archive batch, not a whole-request mutex; cleanup can overlap another run, and a later 409 or 503 can follow batches that already committed. Never interpret a failure or client timeout as proof that nothing changed.

From a scheduler, set `PRODUCT_ANALYTICS_ARCHIVE_TRIGGER_URL` to the full HTTPS endpoint URL, `PRODUCT_ANALYTICS_ARCHIVE_TRIGGER_TOKEN` to the same secret, and optionally `PRODUCT_ANALYTICS_ARCHIVE_TRIGGER_TIMEOUT_SECONDS` (1–3600; default 1800). Run `python -m scripts.trigger_product_analytics_archive`. It follows `has_more` with up to `PRODUCT_ANALYTICS_ARCHIVE_TRIGGER_MAX_REQUESTS` calls (default 20, range 1–100), refuses redirects and non-HTTPS URLs except local loopback, validates each success response and returns non-zero on a request failure, non-200 response or remaining possible backlog at the request limit. It does not retry automatically; check backend logs before retrying after a timeout, since the outcome may be unknown. Schedule the separate R2 staging reconciliation as described below.

**Hosting requirement:** each R2 operation may wait up to the configured storage deadline (default 240 seconds), and one request can make several operations and process both tables. The HTTP client's timeout does not extend a serverless host's execution limit. Do not schedule this endpoint until the target service, proxy and scheduler time limits have been verified to accommodate the run; otherwise use the existing CLI as a separately hosted job. A killed request may leave an unregistered R2 object; archive-before-delete transaction and reconciliation rules still apply. Do not assume an in-process background task survives the response.

What one live run does, for the configured `HUB_ENVIRONMENT` only:

1. Refuses unless the Hub tables (`nav_tabs`, `tabs`, `gridstacks`, `components`) have rows. A database without them is a wrong `DATABASE_URL_V2`, a partial restore or a fresh schema, in which every bound row would look deleted. An environment that holds no analytics rows at all is exempt (a fresh or reset deployment has nothing to delete); the first analytics row of that environment brings the guard back.
2. Deletes records reliably tied to deleted Hub resources (the same rule as `purge_product_analytics_events.py`, see `PRODUCT_ANALYTICS_EVENTS.md`, "Retention"). These are **deleted, not archived**. Only resource existence is checked; access control, edit locks and availability play no part, so an inaccessible or temporarily unavailable resource is never treated as deleted.
3. For each table, archives records older than the retention cutoff in bounded batches: each batch is **uploaded to a random staging key, promoted to its final key by a server-side copy that is conditional on the final key being absent, read back and verified**, then **registered** in `hub_product_analytics_archives` and its rows deleted, in one transaction; the staging object is deleted after the commit. Rows that match the deleted-resource rule are excluded from this selection as well (even with `--skip-deleted-cleanup`), and the Hub rows a batch depends on are **row-locked** from before the upload until the batch commits (see "Resource deletion vs. archiving").

**What an archive is.** An object in the bucket is an archive only if its key is a row in `hub_product_analytics_archives` (the registry, created by `python -m scripts.create_product_analytics_archive_tables`). The job cannot cancel an HTTP request it has given up on — after a deadline, a lost connection or a killed process the server-side outcome of a `PUT` is unknown and the object may still appear later — so the registry, written in the same transaction that verified the bytes, held the locks and deleted the rows, is the authority. Unregistered objects are **leftovers**, not archives: nothing reads them. A staging leftover (`…/_staging/…`) is deleted by the reconciliation after a grace period; a leftover under a final key is reported and classified, never deleted automatically, and is only ever registered by a later run that rebuilds the identical bytes for the identical rows (see "Leftover objects").

## Commands

```
python -m scripts.archive_product_analytics --dry-run         # counts and planned batches; no storage call, no write
python -m scripts.archive_product_analytics --probe-storage   # read-only HEAD on the bucket with the configured credentials
python -m scripts.archive_product_analytics                   # the job
python -m scripts.archive_product_analytics --batch-size 2000 --max-batches 10   # bounded catch-up run
```

| Option | Meaning |
|---|---|
| `--dry-run` | Print, per table, how many rows reference deleted resources (would be deleted) and how many age-expired rows would be archived in how many batches, plus the registry identity (or that it is not initialised), its storage binding, the lock modes and the View As policy. **Read-only**: no upload, no HEAD, no database write of any kind — it neither initialises nor binds the identity (proven on a `READ ONLY` PostgreSQL connection by `test_dry_run_and_report_only_reconciliation_run_inside_read_only_transactions`). If storage configuration is missing or invalid, says so and exits 0; the live job would refuse. |
| `--probe-storage` | `HEAD` on the bucket only, then exit. Use once after deployment to confirm credentials and bucket name. |
| `--batch-size` | Rows per archive object and per delete transaction, 100–50,000 (default 5,000). |
| `--max-batches` | Stop after this many batches per table (also bounds the deleted-resource cleanup). The next run resumes. |
| `--skip-deleted-cleanup` | Leave deleted-resource rows in place. They are still excluded from new archives. |
| `--check-keys FILE` | Read object keys (one per line, from a bucket listing) and report which are registered archives and which are unregistered leftovers; prints the registry summary. No storage call, no write. The reconciliation script below does the listing itself. |

Separate operator commands (own scripts, own identities):

```
python -m scripts.reconcile_product_analytics_archives                 # report leftovers; deletes nothing
python -m scripts.reconcile_product_analytics_archives --delete        # delete STAGING leftovers older than the grace period; classify (never delete) final-key leftovers
python -m scripts.restore_product_analytics_archive --key K --dry-run  # verify a registered archive against registry and bucket; write nothing
python -m scripts.restore_product_analytics_archive --key K            # restore its records (idempotent; deleted-resource records skipped)
```

Exit codes: `0` done (also "retention disabled" and "nothing to do"); `1` a batch failed — that batch and everything after it were neither registered nor deleted — or a precondition could not be evaluated ("archive failed before any deletion"); `2` configuration refused (missing registry or identity table, bad settings, empty Hub tables, identity bound to other storage) — nothing touched; `3` another run holds the batch lock — this run stops, batches it completed earlier are archived normally. **Order of a live run:** every precondition is evaluated first — registry and identity tables present, Hub tables non-empty, storage configuration valid, identity binding compatible with the configured bucket/prefix — then the identity is initialised/bound (the run's only non-destructive write), and only then does the deleted-resource cleanup delete anything, followed by the archive batches. A refusal therefore always means "Nothing was deleted or uploaded" literally. A failure later in the run says exactly what had already been committed before it (`Before this, the cleanup had deleted N events, M engagements … ; archived and deleted in committed batches: …`); the job never says nothing was deleted once the cleanup has run. The cleanup itself runs one committed batch per call, so a database failure inside it (`cleanup failed for <table>: <error type>. The failing batch was rolled back; no archive batch was started. Before this, …`) leaves the earlier batches committed, rolls back only the failing one, exits 1 and starts no archive batch — `test_a_cleanup_batch_failing_after_earlier_batches_committed_is_reported_exactly` injects a real lock conflict after the first committed batch and before the first commit. The job prints counts, the cutoff date, object keys and SHA-256 prefixes only: never row contents, never credentials.

## Required configuration

| Variable | Purpose |
|---|---|
| `HUB_ENVIRONMENT` | `sandbox` or `production` (or `local`). The job archives and deletes only rows stamped with this value and refuses anything else. |
| `PRODUCT_ANALYTICS_RETENTION_DAYS` | Default `365`; `0`/`off` disables the job (exit 0, nothing touched); outside 30–3650 refuses (exit 2). Rows are selected when `occurred_at` (events) or `ended_at` (intervals) is **strictly older** than `now − days`. |
| `R2_ACCOUNT_ID` | Cloudflare account id; the S3 endpoint is `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`. |
| `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | The **writer** token's S3 credentials. Scope the token to **this bucket only** with **Object Read & Write** (the job needs `PutObject`, `CopyObject`, `GetObject`, `HeadObject`, `HeadBucket`, and `DeleteObject` for its own staging objects). Cloudflare's token levels cannot exclude delete or list, so the restriction is in the code — `R2ArchiveStore` has no list operation and deletes staging keys only — and **the token is not the boundary**. Do not reuse an account-wide token. The restore script uses this token's read access. |
| `R2_RECONCILE_ACCESS_KEY_ID`, `R2_RECONCILE_SECRET_ACCESS_KEY` | Credentials for `scripts/reconcile_product_analytics_archives.py` only. Intended to be a **second** `Object Read & Write` token scoped to this bucket (Cloudflare offers no write-without-delete level); until Chris creates it they may hold the same values as the writer's, which keeps the separation code-only. The reconciliation lists, reads and deletes **staging** objects; `R2ReconcileStore` has no operation that writes or that deletes an object under a final key. Never set on the API or on the writer's schedule. |
| `R2_BUCKET_NAME` | The private bucket created for this purpose (`renphil-hub-analytics-archive-bucket`). Use **separate buckets or at least separate prefixes per environment**; the key layout below already separates environments, but a separate bucket per environment also separates credentials. |
| `PRODUCT_ANALYTICS_ARCHIVE_PREFIX` | Key prefix, default `hub-product-analytics`. |
| `PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS` | `omit` (default) or `include`: whether archives carry the `view_as_*` diagnostics. `include` must be set explicitly; any other value refuses the job. See "Privacy". |
| `DATABASE_URL_V2` | The same database the backend uses (the Hub tables and the registry table must be there). The dev value is Neon's **pooled** endpoint (PgBouncer, transaction pooling). The job is written for that: it uses no session state — `SET LOCAL` only, a transaction-level advisory lock, row locks inside one transaction, no temp tables, no server-side prepared statements — so it is correct on the pooled and on the direct endpoint. Validate before scheduling: `--dry-run` prints the lock modes it read from the catalog, and `tests/test_product_analytics_archive_postgres.py` exercises every lock on a direct connection; what is **not** verified here is the pooler itself (see "Before scheduling"). |

All four `R2_*` values are validated before any database work (`R2Config.from_settings`); error messages name the variable, never its value, and the config object's `repr` omits secrets. The values live only in the deployment's environment/secret store, never in the repository, `.env.example`, logs or chat.

Bucket requirements: private (no public access, no public bucket URL), R2's default encryption at rest, (R2 offers neither object versioning nor Object Lock, so protection against overwrites or deletions by a token holder does not exist at the bucket level; the job never overwrites a final-key object it has seen and deletes only its own staging objects). Readers of the archive need their own read-only token; nothing in the application reads the bucket.

## Archive format (`format_version` 3)

One ZIP object per batch, per table, containing exactly:

| Member | Contents |
|---|---|
| `manifest.json` | `format_version`, `environment`, `events`/`engagements` row counts, `record_types`, `time_range` (UTC min/max of `occurred_at` / `ended_at`), `id_range` (database ids), `columns` per table, `members` (per member: `sha256`, `bytes`, `rows`), `record_digest` (SHA-256 over the sorted `event_id`/`engagement_id` list), `metadata` (`table`, `selection`). |
| `events.jsonl` | One JSON object per event row: every column of `hub_product_events`, timestamps as UTC ISO-8601, `properties` as an object. Empty in an engagements archive. |
| `engagements.jsonl` | One JSON object per active-time interval, every column of `hub_product_engagements`. Empty in an events archive. |

Rows are archived with every column except what `PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS` excludes (see "Privacy"): `actor_email`, `hub_user_id`, `page_id`, `component_id`, `target_id` and the timestamps are always present, because the archive is the only remaining copy once the rows are deleted. That makes the bucket personal-data storage: restrict readers accordingly and apply the same data-subject handling as the database. The manifest's `columns` lists exactly what each record carries and `omitted_columns` what was left out.

## Privacy: the `view_as_*` columns (decided 2026-11-03: omitted by default)

Decision: archives **omit** `view_as_role_key`, `view_as_scope_key` and `view_as_context` unless `PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS=include` is set explicitly. The real actor identity analytics needs (`actor_email`, `hub_user_id`) is always archived. **Omitted diagnostics cannot be restored once the live rows are deleted**: a restore brings those columns back as NULL (`test_restore_of_an_archive_written_under_the_default_policy_leaves_the_view_as_columns_null`); the manifest records them under `omitted_columns` and the registry row carries the same list. The analysis that led here follows.

`view_as_role_key`, `view_as_scope_key` and `view_as_context` record, for a Standard View As session, which role/scope pair (and which simulated user's internal id) the real actor had adopted. Facts: no API, export, Page Insights or workbook ever returns them; nothing restores or analyses them; they exist only "for restricted operational investigation" that has no reader today. A restore of archived rows does not need them (`event_id`/`engagement_id`, actor, environment, bindings and timestamps are complete without them), and a future analytics feature could only use them if that feature were designed first.

Least-data design: archive without them (`PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS=omit`). Effect of omitting: once the rows are deleted, it is permanently impossible to say which View As pair an archived interaction was performed under — acceptable if that investigation capability is not wanted for data older than a year, irreversible otherwise. Effect of including (`include`, the current default): the archive is a lossless copy and the columns can still be stripped later by re-writing archives; the bucket then also holds those diagnostics about every archived actor.

The dry run prints which policy is in effect; `include` is the reversible choice and the one a deployment must ask for.

| Setting | What the archive retains | What a restore recovers | Privacy consequence |
|---|---|---|---|
| `include` | Every column, including `view_as_role_key`, `view_as_scope_key`, `view_as_context` | The exact rows, including under which View As pair each archived interaction ran | The bucket holds, for every archived actor, which roles/scopes they simulated and whom; these diagnostics are kept for as long as the archive exists, in a store outside the database's access controls |
| `omit` | Every column except those three; the manifest records them under `omitted_columns` | The rows without the View As diagnostics: actor, environment, bindings, timestamps and properties are complete, every read the Hub performs works unchanged | Once the live rows are deleted it is permanently impossible to say which View As pair an archived interaction was performed under |

Neither setting changes what any API, export or Page Insight returns: nothing reads these columns today.

The ZIP bytes are **deterministic** for a given ordered set of rows (fixed member timestamps 1980-01-01, sorted JSON keys, no run-specific values inside). The object's S3 metadata carries `sha256` and `format-version`.

Object key: `<prefix>/<environment>/<table>/v3/<YYYY>/<YYYY-MM-DD>_<first id>-<last id>_<first 16 hex of the ZIP's SHA-256>.zip`, where the day is that of the oldest record in the batch. Keys contain no personal data.

`product_analytics_archive.validate_archive(bytes)` checks a downloaded archive end to end (ZIP integrity, version, environment, member digests, sizes and row counts, each record's id and environment) and returns the manifest.

## Guarantees and how they are enforced

| Concern | Behaviour |
|---|---|
| Archive before delete | Per batch, in one database transaction: `SET LOCAL lock_timeout` / `statement_timeout` → `pg_try_advisory_xact_lock` (another run: exit 3) → `SELECT … FOR UPDATE` (the batch) → row locks on the Hub rows the deleted-resource rule consults for the batch (`FOR KEY SHARE` or `FOR SHARE` per the catalog) → re-count the batch against that rule (non-zero: roll back and select again, nothing uploaded) → encode → `ensure_archived` (`HEAD` the final key; conditional `PUT` to a random staging key, server-side `CopyObject` to the final key conditional on its absence — `cf-copy-destination-if-none-match: *`, refused with 412 → verify the competing object in full and reuse it or stop — then `GET` and compare SHA-256; or recognise an existing identical final object), each storage call under a deadline → re-count once more (non-zero is an integrity failure: the run stops, nothing registered or deleted, the object is named) → **register the object** → `DELETE … WHERE id IN (batch ids) AND environment = … AND timestamp < cutoff` → commit → delete the staging object (after the commit, outside the locks; best effort). Only that commit makes the object an archive. Any exception is raised before it, the transaction is rolled back (every lock released, no registry row), the staging object is deleted (best effort) and the run ends. |
| Snapshot consistency (concurrent row changes) | The application never updates analytics rows (ingest is insert-ignore; the only writers are the two cleanup/archive jobs). Independently of that, the batch's rows are **row-locked** (`FOR UPDATE`) from selection to commit, so a concurrent `UPDATE` or `DELETE` of those rows blocks for the duration of one batch's upload and then sees the rows gone (0 rows). The archived bytes are therefore exactly the versions that were deleted; a newer version can never be deleted on the strength of an older archive. On failure or rollback the locks are released and the untouched rows are selected again by the next run (then with whatever version they have at that time). Proven on PostgreSQL by `test_rows_are_locked_while_their_archive_uploads_so_a_concurrent_update_cannot_diverge` and `test_an_upload_failure_releases_the_locks_and_the_pending_deletion_proceeds`. SQLite (tests only) has no row locks. |
| Resource deletion vs. archiving | **A record is archived at the moment `ensure_archived` returns for the object containing it, inside a transaction in which the nav tabs, tabs, sub-gridstacks and components that record depends on are row-locked so that neither the row nor the column the deleted-resource rule joins on can change.** The lock strength is decided from the live catalog (`resource_lock_modes`, printed by the job and by `--dry-run`): `FOR KEY SHARE` — blocks `DELETE` and any change of the join column, nothing else — only where that column has a valid, complete, single-column unique index; otherwise `FOR SHARE`, which blocks every `UPDATE` and `DELETE` of the referenced rows. `document_id` is never unique (the models declare plain indexes), and the dev database has no index at all on `components.link` although the model declares one, so there every referenced row is held `FOR SHARE` (see "Catalog findings"). A deletion already in flight when the batch locks either commits first — then the pre-upload re-count sees it and the batch is selected again without those rows, nothing uploaded — or waits. **No record enters a registered archive after its resource was deleted or re-keyed.** A resource may be deleted after its records were archived (the deletion waits for the batch, then completes); that archive is not reopened, as agreed. What this does **not** cover is bytes the job could not stop: an upload abandoned at the deadline (or by a lost connection or a killed process) can still land in the bucket after the locks are gone and after the resource was deleted — reproduced exactly in `test_a_late_upload_after_the_deadline_can_land_but_is_never_an_archive`. It lands under a **staging** key: never registered, never reused, never read, and deleted by the reconciliation after the grace period (the same test). A promotion copy abandoned the same way can land under a final key; that object is also never registered or reused, and it is reported, never deleted automatically (see "Leftover objects"). Proven on PostgreSQL with real concurrent transactions by `test_lock_strength_follows_the_live_catalog_not_the_models` (an `UPDATE` of each `document_id` and of `components.link` waits; with a unique index the weaker lock is chosen and a title edit proceeds), `test_the_hub_services_own_deletion_and_update_paths_wait_for_the_batch` (the real `delete_tab_subtree_by_document_id_v2` and `update_tab_by_document_id_v2`), `test_deleting_a_resource_the_batch_depends_on_waits_for_the_batch`, `test_a_resource_deleted_between_selection_and_lock_abandons_the_batch_before_any_upload`, `test_a_deletion_in_flight_when_the_batch_locks_is_waited_for_then_the_batch_is_reselected`, `test_the_deleted_resource_cleanup_runs_alongside_an_uploading_batch_without_blocking` and `test_moving_a_component_and_deleting_a_mirror_target_during_the_upload_are_not_blocked`. The cost and its enforced bound are in "Resource deletion vs. archiving: cost" below. |
| Upload or verification failure | Nothing of that batch is registered or deleted; the job exits 1; later batches are not attempted; every lock is released, so a deletion that was waiting completes. The next run selects the same rows again — unless their resource was deleted in between, in which case the cleanup deletes them without archiving. The failed attempt's staging object is deleted at once (best effort; otherwise by the reconciliation); an object it had already promoted to its final key stays an unregistered leftover, reported and never deleted automatically. |
| Session lost before the commit | Registration and deletion are one commit: a session lost after the registry insert but before the commit (`test_a_session_lost_after_registration_before_the_commit_registers_and_deletes_nothing`) leaves no registry row and no deleted row; the staging object is discarded and the promoted final-key object is a leftover until a later run finds the identical object for the identical rows, verifies and registers it. |
| Lock waits | The job never waits longer than `LOCK_TIMEOUT_MS` (5 s) for any lock (a Hub transaction deleting a referenced resource, or another writer of the batch rows). On a timeout the batch is abandoned (nothing uploaded, nothing deleted) and retried up to `LOCK_RETRIES` (3) times; then the run stops with exit 1. The job gives up the batch, never the lock holder. |
| Idle transaction during storage calls | The batch transaction is idle while the storage client works. The managed database closes sessions idle in a transaction for 5 minutes (`idle_in_transaction_session_timeout`, Neon dev, read 2026-11-03); such a close rolls the batch back (nothing deleted; an uploaded object is reused by the next run — `test_a_database_session_closed_during_the_upload_deletes_nothing_and_frees_the_locks`). The job sends a heartbeat statement between consecutive storage calls, and every storage call is abandoned after `PRODUCT_ANALYTICS_ARCHIVE_STORAGE_TIMEOUT_SECONDS` (default 240 s, allowed 1–240 s, enforced in-process by `call_with_deadline`). Verify the target database idle-in-transaction timeout exceeds this deadline with a suitable margin; delays outside the storage call can also consume that margin. |
| Stalled or broken storage | A `PUT`, `COPY` or `GET` that does not return within its configured deadline (default 240 s) raises `ArchiveTimeoutError`: the batch is rolled back, its locks are released, nothing is registered or deleted, the run exits 1. This is **not a cancellation**: the abandoned call keeps running in a daemon thread and may still complete later; the object it produces is unregistered — a staging leftover for a `PUT` (deleted by the reconciliation), a final-key leftover for a `COPY` that commits while the key is still absent (reported only; a late copy onto a key a later attempt has promoted is refused by the destination condition). A closed HTTP connection fails the batch the same way. Tests: `test_a_stalled_upload_is_abandoned_at_the_deadline_and_releases_the_locks`, `test_a_stalled_readback_…`, `test_a_closed_http_connection_fails_the_batch_closed`, `test_a_late_upload_after_the_deadline_can_land_but_is_never_an_archive`. |
| Crash after upload, before delete | The next run rebuilds identical bytes for the same rows, derives the same key, finds the object, reads it back, verifies it inside the locks and registers it with the delete, without uploading again. If the rows are no longer the same (some became deleted-resource rows), the bytes and the key differ and the old object stays an unregistered final-key leftover (reported, classified "not redundant", never deleted automatically). A staging object the crashed run left behind is deleted by the reconciliation. |
| Duplicate / conflicting objects, concurrent writers | Keys embed 16 hex digits of the payload's SHA-256, so two writers can only share a final key when they hold the same bytes. The job never `PUT`s to a final key: it `PUT`s to a random staging key with `If-None-Match: *` (so even a colliding random key is refused rather than overwritten; verified against the real R2 service on 2026-11-04, HTTP 412, and against moto) and promotes by `CopyObject` **conditional on the final key being absent** — R2's beta extension header `cf-copy-destination-if-none-match: *` (Cloudflare "R2 → S3 API → Extensions", read 2026-11-05), refused with HTTP 412, "guaranteed to be checked when the object is committed to the bucket state", like `If-None-Match` on `PutObject`. A writer that commits the key between the job's `HEAD` and its copy therefore gets there first and is **never overwritten**: on the 412 the job `HEAD`s the object, requires the payload's size and every metadata entry it would have stamped (`registry-id`, `environment`, `table`, `sha256`, `format-version`), reads it back and compares the SHA-256; only an object that passes all of it is reused (a late copy of an earlier attempt of the same batch, a concurrent run), anything else — different bytes, different or missing metadata, or no object visible after the 412 (R2 documents that a `NoSuchKey` read is not proof that an unknown write failed) — stops the run (exit 1) with nothing overwritten. Cloudflare documents the destination conditions as **not atomic with the source-side `x-amz-copy-source-if-*` conditions** (the source is selected when the request is made, the destination is checked when the copy commits); the job sends no source condition — its source is its own random staging key, written with `If-None-Match` — and the readback after the copy verifies the bytes that actually reached the final key. **This header makes the copy conditional; it makes nothing about `DeleteObject` conditional.** Evidence: the memory store enforces the condition atomically (`ConditionalPromotionTests`: competing identical object reused, competing different object/metadata refused, vanished object refused, two concurrent promotions commit exactly one, a copy abandoned at the deadline cannot overwrite a later promotion, retry recognises without copying); moto does **not** implement the header — `test_conditional_copy_sends_r2s_destination_header_per_call_and_maps_a_412` proves it is on the wire exactly when asked and that a 412 is mapped, `test_ensure_archived_verifies_a_competing_object_after_a_412_against_the_mock` runs the whole path through the S3 client with a shim that refuses like R2 documents. A sequential real-R2 probe on 2026-11-05, using boto3/botocore 1.43.123 and unique test objects, confirmed successful conditional copy to an absent key, HTTP 412 with the destination unchanged when it existed, an unconditional control copy, and test-object removal. This did not verify concurrent real-R2 copies or run the archive job against the target environment; the header remains beta. Everything a token holder outside the job can do to any object (overwrite, delete) stays outside this design; R2 has no versioning or Object Lock. |
| Concurrent runs | A PostgreSQL **transaction-level** advisory lock (`pg_try_advisory_xact_lock`, key `7206234501`) is taken inside every batch transaction, so it is valid behind a transaction-pooling proxy (a session-level lock would belong to whichever server connection the pooler handed out). A second run stops with exit 3 at its first batch. Even without the lock (SQLite tests), rows are `FOR UPDATE`-locked, the delete is restricted to exact ids and reports what it removed, and the registry insert is `ON CONFLICT (key) DO NOTHING`, so two runs that build the same batch register it once and neither aborts (`test_concurrent_runs_without_a_database_lock_still_delete_each_row_once`, which fails on any worker exception). |
| Deleted-resource cleanup vs. concurrent changes | Each batch is deleted by one statement that re-applies the predicate on the selected ids inside its own snapshot: a resource that exists again (or a component moved back) by the time the DELETE runs keeps its rows; concurrent cleanup runs delete disjoint rows and never fail on each other. Proven on PostgreSQL by `test_concurrent_cleanup_runs_delete_each_stale_row_once_and_keep_live_rows` and `test_cleanup_keeps_rows_whose_resource_exists_again_when_the_delete_runs`. |
| Environment isolation | `environment = HUB_ENVIRONMENT` is part of every selection, every delete and every key. `local` is allowed for operators but never archives Sandbox or Production rows from a shared database. |
| Dry run | Reads counts only. Proven by tests: no store call of any kind, no row written or deleted. |
| Wrong database | Refuses (exit 2) when any Hub table is empty. |
| Retention boundary | Strictly older than the cutoff; a row exactly 365 days old is kept until the next run. |
| Logging | Counts, cutoff date, keys and SHA-256 prefixes. Row contents and credentials never reach stdout or the log. Unexpected exceptions are reported by type; the job's own errors and S3 client errors by message. |

### Resource deletion vs. archiving: cost

The guarantee above is bought with a lock that a Hub deletion has to wait for:

- **Who waits**: a transaction that deletes a nav tab, tab, sub-gridstack or component **referenced by the batch currently uploading** (directly or through the service's cascade) — and, for every table whose join column has no unique index (all four on the dev database; see "Catalog findings"), any **update** of those referenced rows too: a rename, a settings/layout save of the referenced canvas, a content edit or move of the referenced component. Rows the batch does not reference, ingestion and reads are never affected. In practice the batch contains records at least a year old, so the affected rows are pages and widgets that still exist a year after being used.
- **How long**: until that batch commits or rolls back. Typical: seconds for a 5,000-row batch (a few MB). **There is no end-to-end bound the job can guarantee**; what it enforces is a bound per step, and the rest is bounded by the database server or by nothing. The table below is the whole lock-hold path, from the first lock statement to the end of the transaction:

| Step while the locks are held | Bound | Enforced by | Tested by |
|---|---|---|---|
| Remaining lock statements (up to 3 after the first) | 5 s each (`lock_timeout`) | job, `SET LOCAL` | `test_a_deletion_in_flight_when_the_batch_locks…` (timeout path) |
| Pre- and post-upload re-counts, 2 heartbeats, registry insert, `DELETE` (6 statements) | 15 s each (`statement_timeout`) | job, `SET LOCAL` | `test_statements_inside_the_batch_run_under_a_statement_timeout` |
| ZIP encoding + manifest validation of the batch (CPU, in process) | **none** (milliseconds for 5,000 rows; grows with `--batch-size`) | — | — |
| Storage calls: `HEAD`, `PUT` (staging), `COPY`, `GET` (≤ 4 per batch; boto3 at most 2 attempts each, 10 s connect / 45 s read, so ≤ 8 HTTP attempts; the staging delete runs after the commit, outside the locks) | 240 s each by default (`PRODUCT_ANALYTICS_ARCHIVE_STORAGE_TIMEOUT_SECONDS`; range 1–240) — the call is abandoned, **not cancelled** | job, `call_with_deadline` | `test_a_stalled_upload_…`, `test_a_stalled_readback_…`, `test_a_closed_http_connection_…` |
| `COMMIT` | **none** by the job (`statement_timeout` does not cover a commit that is waiting on disk/WAL) | server behaviour only | — |
| Client dies with the transaction open (process killed, host lost) | until the server notices: TCP keepalives (dev server: 60 s idle + 10 s × 6 ≈ 2 min), `client_connection_check_interval` 1 min, and at the latest `idle_in_transaction_session_timeout` (**5 min** on the dev server, from its configuration file — must be confirmed per environment) | server configuration, not the job | `test_a_database_session_closed_during_the_upload…` (server-side termination frees the locks; the job's own death is not simulated) |
| Scheduler stops the job (SIGTERM) | Python exits, the connection closes, the server rolls back at once | OS/driver | — |

  So: at the default deadline, the sum of the listed timer allowances is 3 × 5 + 6 × 15 + 4 × 240 = 1,065 s **plus** encoding and commit, which are not timed; a dead client is bounded only by the server's settings. Smaller `--batch-size` shortens the typical window and the untimed encoding.
- **No server-side cap on the Hub side**: the application's engine sets no `lock_timeout`/`statement_timeout` and the managed database's defaults are 0, so a blocked deletion or edit request waits the full time (an HTTP proxy in front of the API may return an error to the user first; the database transaction still completes once the lock is released — the change is not lost, only late).
- **Measured cost (disposable PostgreSQL 18.6, in-memory storage, 2026-11-03, `hub-analytics-handoff-2026-11-03/locking-investigation/measure_lock_cost.*`)**: one batch of 1,000 rows holds its locks for 0.09 s, one of 5,000 rows (373 KB object) for 0.35 s, including select, lock, encode, store calls, validation, registration and delete; a concurrent rename of the referenced tab started at the upload waited 0.01–0.03 s. Against real R2 the storage calls add their round trips (typically well under a few seconds for a few MB); the enforced per-step bounds above cover the rest. So on today's data the lock cost is milliseconds per nightly batch; it is only a stalled storage service that turns it into the minutes the bounds allow.
- **Index plan (separately reviewable; not run — no index is added to a shared database by this work)**: with a unique index on each join column — `nav_tabs.document_id`, `tabs.document_id`, `gridstacks.document_id`, `components.link` — the job automatically switches those tables to `FOR KEY SHARE`, and only deletions (and re-keys) wait; edits, saves and moves proceed. The dev data allows it today (0 NULLs, 0 duplicate values in all four columns, read 2026-11-03). Suggested form, one per column, outside a transaction, each preceded by a duplicate check: `CREATE UNIQUE INDEX CONCURRENTLY ix_tabs_document_id_uq ON tabs (document_id)` (likewise `ix_nav_tabs_document_id_uq`, `ix_gridstacks_document_id_uq`, `ix_components_link_uq`); the deleted-resource rule and the ingest lookups already assume these values are unique, and the same indexes turn the rule's `NOT EXISTS` sequential scans into index lookups. Given the measured cost, this is an improvement to review on its own, not a prerequisite.

### Catalog findings (Neon dev, read-only, 2026-11-03)

The models are not what the database has: `components.link` is declared `unique=True, index=True` but the dev database has **no index on `link` at all**; `tabs.document_id` and `gridstacks.document_id` have **no index** (the models declare one); `nav_tabs.document_id` has a plain index. Consequences: (1) `FOR KEY SHARE` would not block a change of any join column there, which is why the job reads `pg_index` at run time instead of trusting the models; (2) the deleted-resource rule's `NOT EXISTS` subqueries on `tabs`/`gridstacks`/`components` are sequential scans (30/36/240 rows today — irrelevant now, worth an index before the tables grow). No Hub code path rewrites a `document_id` or a `link` (searched the services for assignments and generic attribute updates: none), so the `FOR SHARE` protection is against a path that does not exist today; it is kept because the guarantee must not depend on that staying true.
- **Deadlocks**: none possible by construction. The job locks analytics rows, then Hub rows; a Hub deletion locks Hub rows only and never touches analytics rows; concurrent archive runs are excluded by the advisory lock; the cleanup's `DELETE` only locks rows that match the deleted-resource rule, which the batch's rows cannot while their resources are locked.
- **Multiple processes**: the locks are PostgreSQL row locks, so they hold across the API process and the job process as long as both use the same database (`DATABASE_URL_V2`).

Alternatives considered and not implemented: (a) accept the race and report it (round 2) — rejected because records of a deleted resource could enter an archive; (b) make the Hub deletion path refuse with "archiving in progress, retry" — a Hub code change and a worse user experience for the same window; (c) stage the object under a temporary key and copy it to the final key — since round 10 every upload is staged and promoted this way, but for the leftover cleanup (see "Leftover objects"), not as a replacement for the locks: the server-side copy cannot be made conditional on the batch being clean, so the row locks and the re-counts remain the guarantee, and staging only changes where an abandoned upload can land. If the wait in (a) is ever unacceptable, (b) is the honest fallback.

### Leftover objects and their reconciliation

**R2 facts this section rests on** (probe against the real service, 2026-11-04, and Cloudflare's S3 compatibility page): `PutObject` honours `If-None-Match: *` (412 on an existing key); `GetObject`/`HeadObject` honour conditional headers; `CopyObject` is implemented, accepts the S3 conditions on the **source** and — as a **beta** R2 extension (Cloudflare "Extensions" page, read 2026-11-05) — `cf-copy-destination-if-none-match` / `-if-match` / `-if-modified-since` / `-if-unmodified-since` on the **destination**, refused with 412 and "checked when the object is committed", documented as **not atomic** relative to the source conditions; `DeleteObject` accepts **no** precondition and no extension header — the probe deleted an object despite a deliberately incorrect `If-Match`; there is no object versioning or Object Lock; lifecycle rules exist; API tokens are bucket-scoped with no "write without delete" level. A HEAD followed by a DELETE is therefore never a compare-and-delete, and nothing here claims it is: **no code path deletes an object under a final key**. The stores have no such operation — `ReconcileStore` offers `delete_staging` only, which raises for any key outside the staging segment (`test_reconcile_store_lists_inspects_and_deletes_staging_objects_only`, `test_reconcile_never_deletes_an_object_under_a_final_key_whatever_its_state`).

**Designs compared (round 10)** for removing abandoned uploads safely:

| Design | Would give | Assessment |
|---|---|---|
| (a) An enforced single writer to the bucket | The job's HEAD would be the only view before its DELETE | Not enforceable on R2: tokens are bucket-wide, the same token writes and deletes, account administrators and every other token holder bypass the job. It can be an operational rule only; this runbook does not call it a security boundary. |
| (b) A backend with atomic conditional delete (S3 `If-Match` on `DeleteObject`, GCS generation preconditions) | Compare-and-delete of final-key leftovers | Not available on R2. Moving the archive to another provider is Chris's decision; the store protocol (`put` with `if_none_match`, `copy`, `delete_staging`) isolates it. |
| (c) **Staging and promotion — implemented** | A staging key is never registered, so nothing at one is or can become an archive; deleting it unconditionally loses nothing, whatever is there | The smallest change that meets the requirement on R2 as it is. The copy is conditional on the final key being absent (`cf-copy-destination-if-none-match: *`), so no final key is ever overwritten by the job; a refused copy is followed by a full verification of the competing object (Guarantees, "Duplicate / conflicting objects"). Residual: a copy the job abandoned can land late under a final key **while that key is still absent** (unregistered, reported, never deleted automatically; it can never replace a later promotion). Sequential conditional and unconditional copy behavior was verified with test objects on real R2 on 2026-11-05; concurrent real-R2 copies and the target archive job remain unverified, and the header remains beta. |
| (d) Manual reconciliation in a maintenance window with writers stopped | Removes the job's own concurrent writes | Stops participating writers only; the HEAD-then-DELETE of a final key is still not a compare-and-delete against anyone else, and it needs a person each time. Kept as the operator procedure for final-key leftovers, deliberately unautomated. |

**Lifecycle of one batch's object:** `HEAD` final key (present and identical → reuse) → `PUT` to `<prefix>/<env>/_staging/<uuid>.zip` (`If-None-Match: *`, random key) → `CopyObject` to the content-addressed final key (`MetadataDirective=COPY`, `cf-copy-destination-if-none-match: *`; on 412: `HEAD` + metadata check + `GET` of the competing object, reuse only if identical in every respect, otherwise stop) → `GET` final key, compare SHA-256 → register, delete rows, commit → `DeleteObject` on the staging key (after the commit; best effort, a failure is printed as a note). On any failure between the staging `PUT` and the commit the transaction is rolled back first and the staging object is deleted at once (best effort). `register_archive` refuses a staging key, `ensure_archived` refuses one as an archive key. Tests: `test_the_job_stages_every_upload_promotes_by_copy_and_never_puts_to_a_final_key`, `test_a_staging_key_is_never_registered_or_used_as_an_archive_key`, `test_a_staging_object_that_cannot_be_deleted_after_the_commit_does_not_fail_the_batch`, `test_a_staged_upload_is_promoted_by_a_server_side_copy_that_keeps_its_metadata` (moto).

**What can remain in the bucket, and for how long:**

| Leftover | How it arises | What happens to it | Bytes remain for |
|---|---|---|---|
| Staging object (`…/_staging/…`) | A staging `PUT` abandoned at the deadline (or by a lost connection or a killed process) that lands later — `test_a_late_upload_after_the_deadline_can_land_but_is_never_an_archive`, `test_a_late_upload_is_reconciled_only_after_the_grace_period_and_never_registered`; a staging delete that failed after the commit | `reconcile --delete` deletes it once it is older than the grace period (24 h default, at least 1 h), under the job lock, after a registry re-check and an ownership check (`registry-id` metadata equals this database's identity; anything else is retained as foreign). No content comparison: none is needed, and a replacement after the HEAD is deleted just the same (`test_a_staging_object_replaced_before_its_deletion_is_still_deleted_and_a_final_object_never_is`). | Grace period plus the reconciliation's interval: with a daily schedule, about one to two days. Never an archive at any point. |
| Unregistered object under a final key | A `CopyObject` abandoned at the deadline that lands later while the key is still absent (it cannot replace a later promotion); a batch that failed after the copy (readback mismatch, lost session, crash before the commit); an object another writer put there | Listed every run. With `--delete` also downloaded and classified under the job lock: **redundant** (every record has a byte-identical live row, rows locked `FOR SHARE` during the comparison — the next archive run rebuilds the same bytes, finds the object under the same key, verifies and registers it: `test_a_promotion_that_landed_but_was_never_committed_is_a_final_leftover_the_next_run_registers`), **not redundant** (a record missing or changed — typically rows the cleanup deleted as deleted-resource rows), **invalid**, **foreign**. **Never deleted by this code.** | Redundant: until the next archive run registers it (normally the next day). Otherwise: until an operator deletes it by hand after review (design (d): pause the job's schedule, confirm with `--check-keys` that the key is not registered, delete it with the dashboard or the operator's own tooling, resume). |
| Registered archive | — | Never a candidate. A registered key whose object is not listed, or a registered key under `…/_staging/`, is an `ALERT` line and exit 1. | — |

**Trust boundary, stated plainly.** The staging-only rule, the ownership marker, the grace period and the registry re-check are checks in this code. They are not enforced by R2 or by the tokens: whoever holds a bucket token — ours or any other — can put, overwrite or delete any object, registered archives included; a clone of the database with the same identity row and the same token could delete the original's staging objects (harmless) but is refused for anything else by the storage binding. The scheduled job and the reconciliation are the only writers this design accounts for. Do not apply a lifecycle rule to the archive prefixes. A rule scoped to `<prefix>/<env>/_staging/` only (expire after ≥ 2 days) would be safe by the same argument as the reconciliation and is optional; it is neither required nor configured by this work.

Separate deployments need separate buckets or prefixes (the identity's storage binding refuses a mismatch); the pooled endpoint, deployment credentials and the target prefixes still need the validation listed under "Scheduling" before anything is scheduled.

Known limitations:

- Row locks hold for one batch's upload (seconds for 5,000 rows): a concurrent writer of those exact analytics rows — in practice only another cleanup/archive run, which the advisory lock already excludes — waits that long, and a deletion (and, under `FOR SHARE`, an edit) of a referenced Hub resource waits as described above.
- On a database without row locks (SQLite, tests only) the resource guarantee degrades to the post-upload check: the batch is not registered or deleted and the run stops, but the promoted object exists as a final-key leftover.
- A final-key leftover can remain whenever a batch's promotion reached the service but its commit did not happen (deadline on the copy, readback failure, lost session, crash). Its records were captured while their resources were locked, except in the late-landing case above. It is never an archive; readers start from the registry and must still **de-duplicate by `event_id` / `engagement_id`** (a row can be in a leftover and in a later archive) and apply the deleted-resource rule and their permissions at read time. Tests: `test_a_rollback_after_the_upload_leaves_an_orphan_captured_while_its_resources_existed`, `test_a_session_lost_after_registration_before_the_commit_registers_and_deletes_nothing`.
- The readback doubles the download volume of each batch; keep `--batch-size` moderate (5,000 rows is a few MB).
- Durability beyond "the object exists and reads back identically" is R2's: this job does not maintain a second copy or a cross-region replica.
- Deleting a resource **after** its records were archived does not reopen or rewrite existing archives (accepted by Chris, 2026-11-02). Archived statistics therefore still contain rows for pages, tabs and components that no longer exist, and rows an editor may no longer be allowed to see.

## Loading archived statistics later

Nothing in the Hub reads the archive today. Any future loader must, at read time:

0. Start from the registry (`hub_product_analytics_archives`), never from a bucket listing: only registered keys are archives; an unregistered object is a leftover that may hold records of deleted resources.
1. Validate each archive (`validate_archive`, and compare its SHA-256 with the registry row) and de-duplicate rows by `event_id` / `engagement_id` across archives.
2. Apply the **current** deleted-resource rule: drop rows whose verified bindings (`page_id`, `component_id`, `target_id`, `nav_tab_id`, `tab_id`) point at resources that no longer exist, exactly as `_deleted_page_predicate` does for live rows. Archived rows are never backfilled or rebound.
3. Apply the reader's **current** permissions with the same live access fold the API uses (`filter_editable_events`, `filter_editable_engagements`, `resolve_names`): an editor who lost access to a page since the archive was written must not receive its rows; only All Scopes admins see people.
4. Treat archived `view_as_*` fields as internal diagnostics that are never returned.

## Scheduling

- Run once a day per environment that records analytics, with the backend's normal environment variables plus the four `R2_*` values, after the API deployment that contains this code and after `python -m scripts.create_product_analytics_tables` **and** `python -m scripts.create_product_analytics_archive_tables` (the registry) have been run. Suggested: 03:30 UTC, after the host's backup window, as a Render cron job / GitHub Actions `schedule` / host cron invoking `python -m scripts.archive_product_analytics`.
- Before scheduling, on the target database: confirm `SHOW idle_in_transaction_session_timeout` (the only bound on a dead client's locks) and whether `DATABASE_URL_V2` is the pooled endpoint; on the pooled endpoint run `--dry-run` and one bounded live run and confirm the output shows the lock-mode line and `registered` per batch — the pooler was **not** exercised by the test suite (which uses a direct connection), only designed for.
- Reconciliation: schedule `python -m scripts.reconcile_product_analytics_archives --delete` daily per environment, with the `R2_RECONCILE_*` token, after the archive job's slot. It deletes staging leftovers older than the grace period and classifies final-key leftovers, which it never deletes. Alert on exit 1 (a deletion failed, a registered archive is missing its object, or a registered key under `_staging/`) and on repeated 3.
- Before enabling, run the reviewed probe against the real bucket with **test keys only** (never under a deployment's archive prefix): conditional `PutObject` (done 2026-11-04: HTTP 412), readback, metadata round trip and exact-key listing (done 2026-11-04); **`CopyObject` of a staged test object to a test final key with `MetadataDirective=COPY` and `cf-copy-destination-if-none-match: *`, then `HeadObject` on the copy to confirm size, SHA-256 metadata and `registry-id`; then the same `CopyObject` again onto the now-existing test key, which must return HTTP 412 and leave the object unchanged (ETag, size, metadata, `LastModified`); and once without the header, which overwrites (to confirm the header, not the mock, is what refuses) — sequential cases verified on 2026-11-05 with boto3/botocore 1.43.123 and unique test keys; concurrent real-R2 copy is untested and the header remains beta**; `DeleteObject` of the staged test key and of the test copy (not yet done through this code's `delete_staging`). That R2 ignores `If-Match` on `DeleteObject` was established 2026-11-04 and nothing relies on it any more. Then a dry run and one bounded live run on the pooled endpoint, and one report-only reconciliation.
- Do not run the job for a database from more than one scheduler at once (the lock makes the second exit 3, but the schedule should not rely on it).
- A missed day only delays archiving by a day. Catch-up after a long gap: `--max-batches` to bound each run.

## Monitoring

- Alert on exit code `1` (failed batch) and on repeated `3` (a run never finishing). `2` on a scheduled run means configuration drift.
- Keep the job output (it is safe): per-batch lines with key, SHA-256 prefix, `uploaded` vs `already present`, and `deleted N`. `deleted` lower than the batch size on a batch that was not the last one indicates concurrent deletion; investigate if it repeats.
- The run's first archive line, `resource locks while a batch uploads: …`, states which lock each Hub table gets and why; `FOR SHARE` on a table means edits of referenced rows wait (see the cost section and the index suggestion).
- `note: … re-selected …` lines mean a Hub resource was deleted between a batch's selection and its lock (nothing was uploaded; harmless). `note: … waited more than … ms for Hub rows …` means a Hub transaction held a referenced resource for longer than the lock timeout; repeated occurrences point at a long-running deletion or an idle transaction on the API side. An `ArchiveIntegrityError … came to reference a deleted resource while … was uploaded` must not occur on PostgreSQL; if it does, the row locks were bypassed (treat as an incident: the named object holds records of a deleted resource; nothing was deleted from the database).
- Track the bucket's object count and size growth against the dry-run counts; a run that uploads but reports `deleted 0` repeatedly indicates the delete is being refused (lock, permissions) and must be investigated before the bucket fills with duplicates.
- Dry-run counts can be compared with `SELECT count(*) … WHERE occurred_at < now() - interval '365 days'` to spot a selection bug.
- `ArchiveIntegrityError: an object already exists at … was not overwritten` means a writer committed the job's exact key with something other than the job's bytes and metadata between the job's HEAD and its copy; nothing was overwritten or deleted. Treat as an incident (who writes to the archive prefix?).
- Reconciliation output: `deleted staging leftover: …` lines are routine after a job failure or timeout; `note: the staging object of this batch could not be deleted now …` in the job's output means the reconciliation will do it. `leftover under a final key …` lines should be rare and each deserves a look: `retained (redundant: …)` ones disappear after the next archive run registers them, `retained (… operator review required)` ones are an operator's decision (design (d) in "Leftover objects"). Any `ALERT:` line is exit 1.

## Recovery

- **Job failed (exit 1)**: nothing of the failed batch was deleted. Fix the cause (credentials, network, bucket), rerun. If the message is "an object already exists at … with different content" (or "… with different content or metadata; it was not overwritten", "… no object is visible there now"), do not delete anything: download both candidates, inspect, and only then decide whether the existing object may be renamed by an operator; the job's own staging object was discarded, the rows are still live and are selected again by the next run.
- **Interrupted run**: rerun; identical batches are recognised and not re-uploaded.
- **Restore rows from an archive** — `python -m scripts.restore_product_analytics_archive --key <key> [--dry-run] [--include-deleted-resources]` (entry point `restore_registered_archive`). It starts from the registry, never from the bucket: the key must be registered for this `HUB_ENVIRONMENT`; the object is downloaded and must have the registered SHA-256; it must validate as a supported format (v2 or v3) and carry the registered environment and record count; only then are the JSONL records inserted. An unregistered leftover, a tampered or replaced object, a missing object or an archive of another environment is refused and **nothing is written**; `--dry-run` runs every check and the download and writes nothing. Restore is idempotent (a record already present, by `event_id`/`engagement_id`, is left untouched); `id` is assigned anew; columns the archive omitted come back NULL — under the default policy that is the View As diagnostics, which **cannot be recovered once the live rows were deleted**. Records that match the deleted-resource rule at restore time are removed again in the same transaction and counted as `skipped`; `--include-deleted-resources` is the explicit recovery mode that keeps them (they then stay until the next cleanup). The raw insertion helper (`_insert_trusted_archive_rows`) is internal: it trusts its input and must only ever receive bytes the entry point verified. Restored rows are age-expired again and are re-archived by the next run under a new key unless retention is disabled. Tests: `test_restore_from_a_registered_archive_round_trips_every_column_and_is_idempotent`, `test_restore_starts_from_the_registry_and_refuses_everything_else_without_writing`, `test_restore_skips_records_of_deleted_resources_unless_recovery_mode_is_explicit`, `test_restore_of_an_archive_written_under_the_default_policy_leaves_the_view_as_columns_null`, `test_restore_script_reports_and_refuses_like_the_entry_point`, `test_restore_skips_deleted_resource_records_using_the_real_predicate` (PostgreSQL).
- **Leftover objects**: see "Leftover objects and their reconciliation". `reconcile --delete` (separate token) removes staging leftovers after the grace period; until then a staging leftover may hold records (including, in the late-landing case, records of a resource deleted after the job gave up) as bytes in the bucket that nothing in the Hub can read. A final-key leftover is listed and classified every run and is never deleted by the code: a redundant one is registered by the next run that rebuilds the identical bytes for the identical rows; any other one stays until an operator deletes it after review; a fresh object is written for the rows meanwhile.
- **Registry damage**: the registry is the list of archives. Back it up with the database; if a row is lost, the object becomes a final-key leftover (invisible to readers; the reconciliation classifies it as not redundant, since its rows are gone, and retains it — it never deletes an object under a final key) and its rows are already deleted — recover by re-registering from the object: `validate_archive`, then insert the registry row from the manifest (`register_archive`) in a transaction, after confirming the key against the bucket.
- **Rollback of a bad deployment**: the archive job is a separate process; disabling its schedule (or setting `PRODUCT_ANALYTICS_RETENTION_DAYS=off`) stops all deletion immediately. Archives already written stay valid.

### CSV inspection files (format v3)

Each ZIP also contains `events.csv` and `engagements.csv`, with headers even for an empty record type. CSV is for inspection; JSONL remains the source for restoration. CSV fields containing JSON are serialized as JSON text, and formula-like cells are prefixed with an apostrophe for spreadsheet safety. The manifest records checksums and row counts for both CSV files; validation regenerates them from the JSONL records and checks they match. The validator continues to accept format v2 archives, which have no CSV files. ZIP contents may include personal information and require the same access controls as the original JSONL.

CSV rules, exactly (`_csv_cell`): a null is an empty cell; a timestamp is UTC ISO-8601; a nested value (JSON object or list) is its canonical JSON text; everything else is its text. A cell whose text, after any leading whitespace (Unicode included) or control characters, starts with `=`, `+`, `-`, `@` or `|`, or whose first character is a control character, is prefixed with `'` so a spreadsheet shows it as text — this also prefixes an honest negative number, which is why the CSV is never the restore source. Column order is the manifest's `columns`; line ends are `\n`; quoting is minimal; the bytes are deterministic. Validation rejects any CSV that is not byte-identical to what the JSONL records regenerate (row or header order, an edited cell, a dropped or appended row, an empty member), any manifest that misstates a CSV digest, size or row count, an extra member, and a manifest claiming v2 while CSV members are present. Objects of format v3 live under `…/v3/…` keys; no v2 object was ever written outside tests (nothing was deployed), so the version bump reuses nothing.

Restore: `product_analytics_archive.restore_archive_rows(db, payload)` validates the archive, inserts its JSONL records into the live tables with `INSERT … ON CONFLICT (event_id | engagement_id) DO NOTHING` (a record already present is left untouched; `id` is assigned anew; columns the archive omitted come back NULL), returns rows inserted per table and leaves the commit to the caller. Restored rows are age-expired again and are re-archived by the next run under a new key unless retention is disabled.
