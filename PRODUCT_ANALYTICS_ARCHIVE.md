# Hub product analytics: archive-before-delete runbook

`scripts/archive_product_analytics.py` is the scheduled retention job for `hub_product_events` and `hub_product_engagements`. It is **not** scheduled or deployed by the application; an operator schedules it per environment after the review below.

What one live run does, for the configured `HUB_ENVIRONMENT` only:

1. Refuses unless the Hub tables (`nav_tabs`, `tabs`, `gridstacks`, `components`) have rows. A database without them is a wrong `DATABASE_URL_V2`, a partial restore or a fresh schema, in which every bound row would look deleted. An environment that holds no analytics rows at all is exempt (a fresh or reset deployment has nothing to delete); the first analytics row of that environment brings the guard back.
2. Deletes records reliably tied to deleted Hub resources (the same rule as `purge_product_analytics_events.py`, see `PRODUCT_ANALYTICS_EVENTS.md`, "Retention"). These are **deleted, not archived**. Only resource existence is checked; access control, edit locks and availability play no part, so an inaccessible or temporarily unavailable resource is never treated as deleted.
3. For each table, archives records older than the retention cutoff in bounded batches: each batch is **uploaded, read back and verified**, then **registered** in `hub_product_analytics_archives` and its rows deleted, in one transaction. Rows that match the deleted-resource rule are excluded from this selection as well (even with `--skip-deleted-cleanup`), and the Hub rows a batch depends on are **row-locked** from before the upload until the batch commits (see "Resource deletion vs. archiving").

**What an archive is.** An object in the bucket is an archive only if its key is a row in `hub_product_analytics_archives` (the registry, created by `python -m scripts.create_product_analytics_archive_tables`). The job cannot cancel an HTTP request it has given up on — after a deadline, a lost connection or a killed process the server-side outcome of a `PUT` is unknown and the object may still appear later — so the registry, written in the same transaction that verified the bytes, held the locks and deleted the rows, is the authority. Unregistered objects are **leftovers**, not archives: nothing reads them, no run reuses them, and `--check-keys` identifies them for reconciliation (see "Leftover objects").

## Commands

```
python -m scripts.archive_product_analytics --dry-run         # counts and planned batches; no storage call, no write
python -m scripts.archive_product_analytics --probe-storage   # read-only HEAD on the bucket with the configured credentials
python -m scripts.archive_product_analytics                   # the job
python -m scripts.archive_product_analytics --batch-size 2000 --max-batches 10   # bounded catch-up run
```

| Option | Meaning |
|---|---|
| `--dry-run` | Print, per table, how many rows reference deleted resources (would be deleted) and how many age-expired rows would be archived in how many batches, plus the registry identity (or that it is not initialised), its storage binding, the lock modes and the View As policy. **Read-only**: no upload, no HEAD, no database write of any kind — it neither initialises nor binds the identity (proven on a `READ ONLY` PostgreSQL connection by `test_dry_run_and_report_only_reconciliation_run_inside_read_only_transactions`). If storage configuration is missing or invalid, says so and exits 0; the live job would refuse. |
| `--probe-storage` | `HEAD` on the bucket only, then exit. Use once after deployment to confirm credentials and bucket name. |
| `--batch-size` | Rows per archive object and per delete transaction, 100–50,000 (default 5,000). |
| `--max-batches` | Stop after this many batches per table (also bounds the deleted-resource cleanup). The next run resumes. |
| `--skip-deleted-cleanup` | Leave deleted-resource rows in place. They are still excluded from new archives. |
| `--check-keys FILE` | Read object keys (one per line, from a bucket listing) and report which are registered archives and which are unregistered leftovers; prints the registry summary. No storage call, no write. The reconciliation script below does the listing itself. |

Separate operator commands (own scripts, own identities):

```
python -m scripts.reconcile_product_analytics_archives                 # report leftovers; deletes nothing
# R2 leftover deletion is disabled; reconciliation is report-only.
python -m scripts.restore_product_analytics_archive --key K --dry-run  # verify a registered archive against registry and bucket; write nothing
python -m scripts.restore_product_analytics_archive --key K            # restore its records (idempotent; deleted-resource records skipped)
```

Exit codes: `0` done (also "retention disabled" and "nothing to do"); `1` a batch failed — that batch and everything after it were neither registered nor deleted — or a precondition could not be evaluated ("archive failed before any deletion"); `2` configuration refused (missing registry or identity table, bad settings, empty Hub tables, identity bound to other storage) — nothing touched; `3` another run holds the batch lock — this run stops, batches it completed earlier are archived normally. **Order of a live run:** every precondition is evaluated first — registry and identity tables present, Hub tables non-empty, storage configuration valid, identity binding compatible with the configured bucket/prefix — then the identity is initialised/bound (the run's only non-destructive write), and only then does the deleted-resource cleanup delete anything, followed by the archive batches. A refusal therefore always means "Nothing was deleted or uploaded" literally. A failure later in the run says exactly what had already been committed before it (`Before this, the cleanup had deleted N events, M engagements … ; archived and deleted in committed batches: …`); the job never says nothing was deleted once the cleanup has run. The cleanup itself runs one committed batch per call, so a database failure inside it (`cleanup failed for <table>: <error type>. The failing batch was rolled back; no archive batch was started. Before this, …`) leaves the earlier batches committed, rolls back only the failing one, exits 1 and starts no archive batch — `test_a_cleanup_batch_failing_after_earlier_batches_committed_is_reported_exactly` injects a real lock conflict after the first committed batch and before the first commit. The job prints counts, the cutoff date, object keys and SHA-256 prefixes only: never row contents, never credentials.

Validate before scheduling: `--dry-run` prints the lock modes it read from the catalog, and `tests/test_product_analytics_archive_postgres.py` exercises every lock on a direct connection; what is **not** verified here is the pooler itself (see "Before scheduling"). |

All four `R2_*` values are validated before any database work (`R2Config.from_settings`); error messages name the variable, never its value, and the config object's `repr` omits secrets. The values live only in the deployment's environment/secret store, never in the repository, `.env.example`, logs or chat.

Bucket requirements: private (no public access, no public bucket URL), R2's default encryption at rest, object versioning or a retention lock if the organisation wants protection against accidental overwrites (the job itself never overwrites or deletes objects). Readers of the archive need their own read-only token; nothing in the application reads the bucket.

## Archive format (`format_version` 3)

One ZIP object per batch, per table, containing exactly:

| Member | Contents |
|---|---|
| `manifest.json` | `format_version`, `environment`, `events`/`engagements` row counts, `record_types`, `time_range` (UTC min/max of `occurred_at` / `ended_at`), `id_range` (database ids), `columns` per table, `members` (per member: `sha256`, `bytes`, `rows`), `record_digest` (SHA-256 over the sorted `event_id`/`engagement_id` list), `metadata` (`table`, `selection`). |
| `events.jsonl` | One JSON object per event row: every column of `hub_product_events`, timestamps as UTC ISO-8601, `properties` as an object. Empty in an engagements archive. |
| `engagements.jsonl` | One JSON object per active-time interval, every column of `hub_product_engagements`. Empty in an events archive. |

Rows are archived with every column except what `PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS` excludes (see "Privacy"): `actor_email`, `hub_user_id`, `page_id`, `component_id`, `target_id` and the timestamps are always present, because the archive is the only remaining copy once the rows are deleted. That makes the bucket personal-data storage: restrict readers accordingly and apply the same data-subject handling as the database. The manifest's `columns` lists exactly what each record carries and `omitted_columns` what was left out.

## Privacy: the `view_as_*` columns (decided 2026-11-03: omitted by default)

Decision: archives **omit** `view_as_role_key`, `view_as_scope_key` and `view_as_context` unless `PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS=include` is set explicitly. The real actor identity analytics needs (`actor_email`, `hub_user_id`) is always archived. **Omitted diagnostics cannot be restored once the live rows are deleted**: a restore brings those columns back as NULL (`test_restore_of_an_archive_written_under_the_default_policy_leaves_the_view_as_columns_null`); the manifest records them under `omitted_columns` and the registry row carries the same list. The analysis that led here follows.

`view_as_role_key`, `view_as_scope_key` and `view_as_context` record, for a Standard View As session, which role/scope pair (and which simulated user's internal id) the real actor had adopted. Facts: no API, export, Page Insights or workbook ever returns them; nothing restores or analyses them; they exist only "for restricted operational investigation" that has no reader today. A restore of archived rows does not need them (`event_id`/`engagement_id`, actor, environment, bindings and timestamps are complete without them), and a future analytics feature could only use them if that feature were designed first.

Least-data design: archive without them (`PRODUCT_ANALYTICS_ARCHIVE_VIEW_AS=omit`). Effect of omitting: once the rows are deleted, it is permanently impossible to say which View As pair an archived interaction was performed under — acceptable if that investigation capability is not wanted for data older than a year, irreversible otherwise. Effect of including (`include`, the current default): the archive is a lossless copy and the columns can still be stripped later by re-writing archives; the bucket then also holds those diagnostics about every archived actor.

The dry run prints which policy is in effect; `include` is the reversible choice and the one a deployment must ask for.

| Setting | What the archive retains | What a restore recovers | Privacy consequence |
|---|---|---|---|
| `include` | Every column, including `view_as_role_key`, `view_as_scope_key`, `view_as_context` | The exact rows, including under which View As pair each archived interaction ran | The bucket holds, for every archived actor, which roles/scopes they simulated and whom; these diagnostics are kept for as long as the archive exists, in a store outside the database's access controls |
| `omit` | Every column except those three; the manifest records them under `omitted_columns` | The rows without the View As diagnostics: actor, environment, bindings, timestamps and properties are complete, every read the Hub performs works unchanged | Once the live rows are deleted it is permanently impossible to say which View As pair an archived interaction was performed under |

Neither setting changes what any API, export or Page Insight returns: nothing reads these columns today.

The ZIP bytes are **deterministic** for a given ordered set of rows (fixed member timestamps 1980-01-01, sorted JSON keys, no run-specific values inside). The object's S3 metadata carries `sha256` and `format-version`.

Object key: `<prefix>/<environment>/<table>/v3/<YYYY>/<YYYY-MM-DD>_<first id>-<last id>_<first 16 hex of the ZIP's SHA-256>.zip`, where the day is that of the oldest record in the batch. Keys contain no personal data.

`product_analytics_archive.validate_archive(bytes)` checks a downloaded archive end to end (ZIP integrity, version, environment, member digests, sizes and row counts, each record's id and environment) and returns the manifest.

## Guarantees and how they are enforced

| Concern | Behaviour |
|---|---|
| Archive before delete | Per batch, in one database transaction: `SET LOCAL lock_timeout` / `statement_timeout` → `pg_try_advisory_xact_lock` (another run: exit 3) → `SELECT … FOR UPDATE` (the batch) → row locks on the Hub rows the deleted-resource rule consults for the batch (`FOR KEY SHARE` or `FOR SHARE` per the catalog) → re-count the batch against that rule (non-zero: roll back and select again, nothing uploaded) → encode → `ensure_archived` (conditional upload, then `GET` and compare SHA-256; or recognise an existing identical object), each storage call under a deadline → re-count once more (non-zero is an integrity failure: the run stops, nothing registered or deleted, the object is named) → **register the object** → `DELETE … WHERE id IN (batch ids) AND environment = … AND timestamp < cutoff` → commit. Only that commit makes the object an archive. Any exception is raised before it, the transaction is rolled back (every lock released, no registry row) and the run ends. |
| Snapshot consistency (concurrent row changes) | The application never updates analytics rows (ingest is insert-ignore; the only writers are the two cleanup/archive jobs). Independently of that, the batch's rows are **row-locked** (`FOR UPDATE`) from selection to commit, so a concurrent `UPDATE` or `DELETE` of those rows blocks for the duration of one batch's upload and then sees the rows gone (0 rows). The archived bytes are therefore exactly the versions that were deleted; a newer version can never be deleted on the strength of an older archive. On failure or rollback the locks are released and the untouched rows are selected again by the next run (then with whatever version they have at that time). Proven on PostgreSQL by `test_rows_are_locked_while_their_archive_uploads_so_a_concurrent_update_cannot_diverge` and `test_an_upload_failure_releases_the_locks_and_the_pending_deletion_proceeds`. SQLite (tests only) has no row locks. |
| Resource deletion vs. archiving | **A record is archived at the moment `ensure_archived` returns for the object containing it, inside a transaction in which the nav tabs, tabs, sub-gridstacks and components that record depends on are row-locked so that neither the row nor the column the deleted-resource rule joins on can change.** The lock strength is decided from the live catalog (`resource_lock_modes`, printed by the job and by `--dry-run`): `FOR KEY SHARE` — blocks `DELETE` and any change of the join column, nothing else — only where that column has a valid, complete, single-column unique index; otherwise `FOR SHARE`, which blocks every `UPDATE` and `DELETE` of the referenced rows. `document_id` is never unique (the models declare plain indexes), and the dev database has no index at all on `components.link` although the model declares one, so there every referenced row is held `FOR SHARE` (see "Catalog findings"). A deletion already in flight when the batch locks either commits first — then the pre-upload re-count sees it and the batch is selected again without those rows, nothing uploaded — or waits. **No record enters a registered archive after its resource was deleted or re-keyed.** A resource may be deleted after its records were archived (the deletion waits for the batch, then completes); that archive is not reopened, as agreed. What this does **not** cover is bytes the job could not stop: an upload abandoned at the deadline (or by a lost connection or a killed process) can still land in the bucket after the locks are gone and after the resource was deleted — reproduced exactly in `test_a_late_upload_after_the_deadline_can_land_but_is_never_an_archive`. That object is never registered, never reused and never read; it is a leftover to reconcile, and whether leftovers are acceptable is the open decision in "Leftover objects". Proven on PostgreSQL with real concurrent transactions by `test_lock_strength_follows_the_live_catalog_not_the_models` (an `UPDATE` of each `document_id` and of `components.link` waits; with a unique index the weaker lock is chosen and a title edit proceeds), `test_the_hub_services_own_deletion_and_update_paths_wait_for_the_batch` (the real `delete_tab_subtree_by_document_id_v2` and `update_tab_by_document_id_v2`), `test_deleting_a_resource_the_batch_depends_on_waits_for_the_batch`, `test_a_resource_deleted_between_selection_and_lock_abandons_the_batch_before_any_upload`, `test_a_deletion_in_flight_when_the_batch_locks_is_waited_for_then_the_batch_is_reselected`, `test_the_deleted_resource_cleanup_runs_alongside_an_uploading_batch_without_blocking` and `test_moving_a_component_and_deleting_a_mirror_target_during_the_upload_are_not_blocked`. The cost and its enforced bound are in "Resource deletion vs. archiving: cost" below. |
| Upload or verification failure | Nothing of that batch is registered or deleted; the job exits 1; later batches are not attempted; every lock is released, so a deletion that was waiting completes. The next run selects the same rows again — unless their resource was deleted in between, in which case the cleanup deletes them without archiving, and an object the failed attempt may have produced stays an unregistered leftover. |
| Session lost before the commit | Registration and deletion are one commit: a session lost after the registry insert but before the commit (`test_a_session_lost_after_registration_before_the_commit_registers_and_deletes_nothing`) leaves no registry row and no deleted row; the uploaded object is a leftover until a later run finds the identical object for the identical rows, verifies and registers it. |
| Lock waits | The job never waits longer than `LOCK_TIMEOUT_MS` (5 s) for any lock (a Hub transaction deleting a referenced resource, or another writer of the batch rows). On a timeout the batch is abandoned (nothing uploaded, nothing deleted) and retried up to `LOCK_RETRIES` (3) times; then the run stops with exit 1. The job gives up the batch, never the lock holder. |
| Idle transaction during storage calls | The batch transaction is idle while the storage client works. The managed database closes sessions idle in a transaction for 5 minutes (`idle_in_transaction_session_timeout`, Neon dev, read 2026-11-03); such a close rolls the batch back (nothing deleted; an uploaded object is reused by the next run — `test_a_database_session_closed_during_the_upload_deletes_nothing_and_frees_the_locks`). The job sends a heartbeat statement between consecutive storage calls, and every storage call is abandoned after `STORAGE_CALL_DEADLINE_S` (60 s, enforced in-process by `call_with_deadline`, independent of the client's own timeouts), so no idle interval can reach that limit. |
| Stalled or broken storage | A `PUT` or `GET` that does not return within 60 s raises `ArchiveTimeoutError`: the batch is rolled back, its locks are released, nothing is registered or deleted, the run exits 1. This is **not a cancellation**: the abandoned call keeps running in a daemon thread and may still complete later; the object it produces is unregistered (a leftover). A closed HTTP connection fails the batch the same way. Tests: `test_a_stalled_upload_is_abandoned_at_the_deadline_and_releases_the_locks`, `test_a_stalled_readback_…`, `test_a_closed_http_connection_fails_the_batch_closed`, `test_a_late_upload_after_the_deadline_can_land_but_is_never_an_archive`. |
| Crash after upload, before delete | The next run rebuilds identical bytes for the same rows, derives the same key, finds the object, reads it back, verifies it inside the locks and registers it with the delete, without uploading again. If the rows are no longer the same (some became deleted-resource rows), the bytes and the key differ and the old object stays an unregistered leftover. |
| Duplicate / conflicting objects, concurrent writers | Keys embed 16 hex digits of the payload's SHA-256, so two writers can only share a key when they hold the same bytes. The upload is still **conditional** (`If-None-Match: *`): if another writer took the key between the job's HEAD and PUT, the service refuses the PUT with 412 and the job reads the other object back — identical bytes count as archived, different bytes stop the run (exit 1) for a human. A key is never overwritten by the job. R2 compatibility: Cloudflare documents `If-None-Match` on `PutObject` for the S3 API, and boto3 sends it as `IfNoneMatch="*"`; this was verified against moto's S3 mock (HTTP 412), **not yet against the real R2 service** — the probe plan below checks it before scheduling. If the real service ignored the header, the content-addressed key keeps the residual risk to a 64-bit digest collision between different payloads. |
| Concurrent runs | A PostgreSQL **transaction-level** advisory lock (`pg_try_advisory_xact_lock`, key `7206234501`) is taken inside every batch transaction, so it is valid behind a transaction-pooling proxy (a session-level lock would belong to whichever server connection the pooler handed out). A second run stops with exit 3 at its first batch. Even without the lock (SQLite tests), rows are `FOR UPDATE`-locked, the delete is restricted to exact ids and reports what it removed, and the registry insert is `ON CONFLICT (key) DO NOTHING`, so two runs that build the same batch register it once and neither aborts (`test_concurrent_runs_without_a_database_lock_still_delete_each_row_once`, which fails on any worker exception). |
| Deleted-resource cleanup vs. concurrent changes | Each batch is deleted by one statement that re-applies the predicate on the selected ids inside its own snapshot: a resource that exists again (or a component moved back) by the time the DELETE runs keeps its rows; concurrent cleanup runs delete disjoint rows and never fail on each other. Proven on PostgreSQL by `test_concurrent_cleanup_runs_delete_each_stale_row_once_and_keep_live_rows` and `test_cleanup_keeps_rows_whose_resource_exists_again_when_the_delete_runs`. |
| Environment isolation | `environment = HUB_ENVIRONMENT` is part of every selection, every delete and every key. `local` is allowed for operators but never archives Sandbox or Production rows from a shared database. |
| Dry run | Reads counts only. Proven by tests: no store call of any kind, no row written or deleted. |
| Wrong database | Refuses (exit 2) when any Hub table is empty. |
| Retention boundary | Strictly older than the cutoff; a row exactly 365 days old is kept until the next run. |
| Logging | Counts, cutoff date, keys and SHA-256 prefixes. Row contents and credentials never reach stdout or the log. Unexpected exceptions are reported by type; the job's own errors and S3 client errors by message. |

### Resource deletion vs. archiving: cost

The guarantee above is bought with a lock that a Hub deletion has to wait for:

- **Who waits**: a transaction that deletes a nav tab, tab, sub-gridstack or component **referenced by the batch currently uploading** (directly or through the service's cascade) — and, for every table whose join column has no unique index (all four on the dev database; see "Catalog findings"), any **update** of those referenced rows too: a rename, a settings/layout save of the referenced canvas, a content edit or move of the referenced component. Rows the batch does not reference, ingestion and reads are never affected. In practice the batch contains records at least a year old, so the affected rows are pages and widgets that still exist a year after being used.
- **How long**: until that batch commits or rolls back. Typical: seconds for a 5,000-row batch (a few MB). **There is no end-to-end bound the job can guarantee**; what it enforces is a bound per step, and the rest is bounded by the database server or by nothing. The table below is the whole lock-hold path, from the first lock statement to the end of the transaction:

| Step while the locks are held | Bound | Enforced by | Tested by |
|---|---|---|---|
| Remaining lock statements (up to 3 after the first) | 5 s each (`lock_timeout`) | job, `SET LOCAL` | `test_a_deletion_in_flight_when_the_batch_locks…` (timeout path) |
| Pre- and post-upload re-counts, 2 heartbeats, registry insert, `DELETE` (6 statements) | 15 s each (`statement_timeout`) | job, `SET LOCAL` | `test_statements_inside_the_batch_run_under_a_statement_timeout` |
| ZIP encoding + manifest validation of the batch (CPU, in process) | **none** (milliseconds for 5,000 rows; grows with `--batch-size`) | — | — |
| Storage calls: `HEAD`, `PUT`, `GET` (≤ 3 per batch; boto3 at most 2 attempts each, 10 s connect / 45 s read, so ≤ 6 HTTP attempts) | 60 s each (`STORAGE_CALL_DEADLINE_S`) — the call is abandoned, **not cancelled** | job, `call_with_deadline` | `test_a_stalled_upload_…`, `test_a_stalled_readback_…`, `test_a_closed_http_connection_…` |
| `COMMIT` | **none** by the job (`statement_timeout` does not cover a commit that is waiting on disk/WAL) | server behaviour only | — |
| Client dies with the transaction open (process killed, host lost) | until the server notices: TCP keepalives (dev server: 60 s idle + 10 s × 6 ≈ 2 min), `client_connection_check_interval` 1 min, and at the latest `idle_in_transaction_session_timeout` (**5 min** on the dev server, from its configuration file — must be confirmed per environment) | server configuration, not the job | `test_a_database_session_closed_during_the_upload…` (server-side termination frees the locks; the job's own death is not simulated) |
| Scheduler stops the job (SIGTERM) | Python exits, the connection closes, the server rolls back at once | OS/driver | — |

  So: with the job's timers all firing, a batch holds its locks for at most 3 × 5 + 6 × 15 + 3 × 60 = 285 s **plus** encoding and commit, which are not timed; a dead client is bounded only by the server's settings. Smaller `--batch-size` shortens the typical window and the untimed encoding.
- **No server-side cap on the Hub side**: the application's engine sets no `lock_timeout`/`statement_timeout` and the managed database's defaults are 0, so a blocked deletion or edit request waits the full time (an HTTP proxy in front of the API may return an error to the user first; the database transaction still completes once the lock is released — the change is not lost, only late).
- **Measured cost (disposable PostgreSQL 18.6, in-memory storage, 2026-11-03, `hub-analytics-handoff-2026-11-03/locking-investigation/measure_lock_cost.*`)**: one batch of 1,000 rows holds its locks for 0.09 s, one of 5,000 rows (373 KB object) for 0.35 s, including select, lock, encode, store calls, validation, registration and delete; a concurrent rename of the referenced tab started at the upload waited 0.01–0.03 s. Against real R2 the storage calls add their round trips (typically well under a few seconds for a few MB); the enforced per-step bounds above cover the rest. So on today's data the lock cost is milliseconds per nightly batch; it is only a stalled storage service that turns it into the minutes the bounds allow.
- **Index plan (separately reviewable; not run — no index is added to a shared database by this work)**: with a unique index on each join column — `nav_tabs.document_id`, `tabs.document_id`, `gridstacks.document_id`, `components.link` — the job automatically switches those tables to `FOR KEY SHARE`, and only deletions (and re-keys) wait; edits, saves and moves proceed. The dev data allows it today (0 NULLs, 0 duplicate values in all four columns, read 2026-11-03). Suggested form, one per column, outside a transaction, each preceded by a duplicate check: `CREATE UNIQUE INDEX CONCURRENTLY ix_tabs_document_id_uq ON tabs (document_id)` (likewise `ix_nav_tabs_document_id_uq`, `ix_gridstacks_document_id_uq`, `ix_components_link_uq`); the deleted-resource rule and the ingest lookups already assume these values are unique, and the same indexes turn the rule's `NOT EXISTS` sequential scans into index lookups. Given the measured cost, this is an improvement to review on its own, not a prerequisite.

### Catalog findings (Neon dev, read-only, 2026-11-03)

The models are not what the database has: `components.link` is declared `unique=True, index=True` but the dev database has **no index on `link` at all**; `tabs.document_id` and `gridstacks.document_id` have **no index** (the models declare one); `nav_tabs.document_id` has a plain index. Consequences: (1) `FOR KEY SHARE` would not block a change of any join column there, which is why the job reads `pg_index` at run time instead of trusting the models; (2) the deleted-resource rule's `NOT EXISTS` subqueries on `tabs`/`gridstacks`/`components` are sequential scans (30/36/240 rows today — irrelevant now, worth an index before the tables grow). No Hub code path rewrites a `document_id` or a `link` (searched the services for assignments and generic attribute updates: none), so the `FOR SHARE` protection is against a path that does not exist today; it is kept because the guarantee must not depend on that staying true.
- **Deadlocks**: none possible by construction. The job locks analytics rows, then Hub rows; a Hub deletion locks Hub rows only and never touches analytics rows; concurrent archive runs are excluded by the advisory lock; the cleanup's `DELETE` only locks rows that match the deleted-resource rule, which the batch's rows cannot while their resources are locked.
- **Multiple processes**: the locks are PostgreSQL row locks, so they hold across the API process and the job process as long as both use the same database (`DATABASE_URL_V2`).

Alternatives considered and not implemented: (a) accept the race and report it (round 2) — rejected because records of a deleted resource could enter an archive; (b) make the Hub deletion path refuse with "archiving in progress, retry" — a Hub code change and a worse user experience for the same window; (c) stage the object under a temporary key and copy it to the final key only when the batch is clean — needs object delete/copy permissions, still leaves the staged object (containing the records) until it is cleaned up, and relies on R2 conditional semantics for `CopyObject` that are unverified. If the wait in (a) is ever unacceptable, (b) is the honest fallback.

### Leftover objects and their reconciliation

R2 does not enforce conditional `DeleteObject`: our probe deleted an object despite a deliberately incorrect ETag. A HEAD followed by DELETE therefore cannot guarantee that the inspected object is the one deleted. R2 reconciliation is **report-only**. Both `--delete` and `--delete-reviewed` refuse before listing or mutating objects, and `R2ReconcileStore.delete` fails closed as defense in depth. No environment variable or operator flag enables this path.

The archive job may leave unregistered objects, including after an upload times out. They are not usable through the registered-archive restore flow and remain in the bucket. The report identifies candidates and registered objects missing from the listing. Their removal requires a separately designed and reviewed process; stopping writers and manually inspecting a key does not create an atomic compare-and-delete. Do not schedule deletion or apply a lifecycle rule to archive prefixes. A lifecycle rule on a shared archive prefix could delete registered archives as well.

Cloudflare R2 credentials currently permit deletion; the writer's restricted interface is not a token-level permission boundary. Separate deployments need separate storage namespaces, and copied database identities cannot alone distinguish a clone from its source. A test object verified metadata round-trip and exact-key listing; deployment credentials, target prefixes and the pooled endpoint still need validation before scheduling.

Known limitations:

- Row locks hold for one batch's upload (seconds for 5,000 rows): a concurrent writer of those exact analytics rows — in practice only another cleanup/archive run, which the advisory lock already excludes — waits that long, and a deletion (and, under `FOR SHARE`, an edit) of a referenced Hub resource waits as described above.
- On a database without row locks (SQLite, tests only) the resource guarantee degrades to the post-upload check: the batch is not registered or deleted and the run stops, but the object exists as a leftover.
- A leftover object can remain whenever a batch's upload reached the service but its commit did not happen (deadline, readback failure, lost session, crash). Its records were captured while their resources were locked, except in the late-landing case above. It is never an archive; readers start from the registry and must still **de-duplicate by `event_id` / `engagement_id`** (a row can be in a leftover and in a later archive) and apply the deleted-resource rule and their permissions at read time. Tests: `test_a_rollback_after_the_upload_leaves_an_orphan_captured_while_its_resources_existed`, `test_a_session_lost_after_registration_before_the_commit_registers_and_deletes_nothing`.
- The readback doubles the download volume of each batch; keep `--batch-size` moderate (5,000 rows is a few MB).
- Durability beyond "the object exists and reads back identically" is R2's: this job does not maintain a second copy or a cross-region replica.
- Deleting a resource **after** its records were archived does not reopen or rewrite existing archives (accepted by Chris, 2026-11-02). Archived statistics therefore still contain rows for pages, tabs and components that no longer exist, and rows an editor may no longer be allowed to see.

## Loading archived statistics later

Nothing in the Hub reads the archive today. Any future loader must, at read time:

0. Start from the registry (`hub_product_analytics_archives`), never from a bucket listing: only registered keys are archives; an unregistered object is a leftover that may hold records of deleted resources.
1. Validate each archive (`validate_archive`, and compare its SHA-256 with the registry row) and de-duplicate rows by `event_id` / `engagement_id` across archives.
2. Apply the **current** deleted-resource rule: drop rows whose verified bindings (`page_id`, `component_id`, `target_id`, `nav_tab_id`, `tab_id`) point at resources that no longer exist, exactly as `_deleted_page_predicate` does for live rows. Archived rows are never backfilled or rebound.
3. Apply the reader's **current** permissions with the same live access fold the API uses (`filter_editable_events`, `filter_editable_engagements`, `resolve_names`): an editor who lost access to a page since the archive was written must not receive its rows; only All Scopes admins see people.
4. Treat archived `view_as_*` fields as internal diagnostics that are never returned.

- Reconciliation: run report-only; no R2 object deletion is implemented. Review unregistered objects and do not schedule destructive cleanup.
- Before enabling: verify the R2 metadata round trip, listing behavior and credentials using a separately reviewed test probe, then review a dry run and validate the pooled database endpoint. The previous probe established that R2 ignores an incorrect If-Match on DeleteObject; do not rely on conditional deletion.
- Do not run the job for a database from more than one scheduler at once (the lock makes the second exit 3, but the schedule should not rely on it).
- A missed day only delays archiving by a day. Catch-up after a long gap: `--max-batches` to bound each run.

## Monitoring

- Alert on exit code `1` (failed batch) and on repeated `3` (a run never finishing). `2` on a scheduled run means configuration drift.
- Keep the job output (it is safe): per-batch lines with key, SHA-256 prefix, `uploaded` vs `already present`, and `deleted N`. `deleted` lower than the batch size on a batch that was not the last one indicates concurrent deletion; investigate if it repeats.
- The run's first archive line, `resource locks while a batch uploads: …`, states which lock each Hub table gets and why; `FOR SHARE` on a table means edits of referenced rows wait (see the cost section and the index suggestion).
- `note: … re-selected …` lines mean a Hub resource was deleted between a batch's selection and its lock (nothing was uploaded; harmless). `note: … waited more than … ms for Hub rows …` means a Hub transaction held a referenced resource for longer than the lock timeout; repeated occurrences point at a long-running deletion or an idle transaction on the API side. An `ArchiveIntegrityError … came to reference a deleted resource while … was uploaded` must not occur on PostgreSQL; if it does, the row locks were bypassed (treat as an incident: the named object holds records of a deleted resource; nothing was deleted from the database).
- Track the bucket's object count and size growth against the dry-run counts; a run that uploads but reports `deleted 0` repeatedly indicates the delete is being refused (lock, permissions) and must be investigated before the bucket fills with duplicates.
- Dry-run counts can be compared with `SELECT count(*) … WHERE occurred_at < now() - interval '365 days'` to spot a selection bug.

## Recovery

- **Job failed (exit 1)**: nothing of the failed batch was deleted. Fix the cause (credentials, network, bucket), rerun. If the message is "an object already exists at … with different content", do not delete anything: download both candidates, inspect, and only then decide whether the existing object may be renamed by an operator.
- **Interrupted run**: rerun; identical batches are recognised and not re-uploaded.
- **Restore rows from an archive** — `python -m scripts.restore_product_analytics_archive --key <key> [--dry-run] [--include-deleted-resources]` (entry point `restore_registered_archive`). It starts from the registry, never from the bucket: the key must be registered for this `HUB_ENVIRONMENT`; the object is downloaded and must have the registered SHA-256; it must validate as a supported format (v2 or v3) and carry the registered environment and record count; only then are the JSONL records inserted. An unregistered leftover, a tampered or replaced object, a missing object or an archive of another environment is refused and **nothing is written**; `--dry-run` runs every check and the download and writes nothing. Restore is idempotent (a record already present, by `event_id`/`engagement_id`, is left untouched); `id` is assigned anew; columns the archive omitted come back NULL — under the default policy that is the View As diagnostics, which **cannot be recovered once the live rows were deleted**. Records that match the deleted-resource rule at restore time are removed again in the same transaction and counted as `skipped`; `--include-deleted-resources` is the explicit recovery mode that keeps them (they then stay until the next cleanup). The raw insertion helper (`_insert_trusted_archive_rows`) is internal: it trusts its input and must only ever receive bytes the entry point verified. Restored rows are age-expired again and are re-archived by the next run under a new key unless retention is disabled. Tests: `test_restore_from_a_registered_archive_round_trips_every_column_and_is_idempotent`, `test_restore_starts_from_the_registry_and_refuses_everything_else_without_writing`, `test_restore_skips_records_of_deleted_resources_unless_recovery_mode_is_explicit`, `test_restore_of_an_archive_written_under_the_default_policy_leaves_the_view_as_columns_null`, `test_restore_script_reports_and_refuses_like_the_entry_point`, `test_restore_skips_deleted_resource_records_using_the_real_predicate` (PostgreSQL).
- **Leftover objects**: see "Leftover objects and their reconciliation" — report-only, with the separate reconciliation token. R2 deletion is disabled pending a safe design. Until the reconciliation has run, a leftover may hold records (including, in the late-landing case, records of a resource deleted after the job gave up) as bytes in the bucket; nothing in the Hub can read them and nothing else removes them. A leftover that is later needed (a batch whose rows are still in the database) is never used as is: the next run re-verifies and registers it only if it is byte-identical to the batch it rebuilds; otherwise it stays a leftover and a fresh object is written.
- **Registry damage**: the registry is the list of archives. Back it up with the database; if a row is lost, the object becomes a leftover (invisible to readers, and the reconciliation would delete it after the grace period — stop the reconciliation first) and its rows are already deleted — recover by re-registering from the object: `validate_archive`, then insert the registry row from the manifest (`register_archive`) in a transaction, after confirming the key against the bucket.
- **Rollback of a bad deployment**: the archive job is a separate process; disabling its schedule (or setting `PRODUCT_ANALYTICS_RETENTION_DAYS=off`) stops all deletion immediately. Archives already written stay valid.

### CSV inspection files (format v3)

Each ZIP also contains `events.csv` and `engagements.csv`, with headers even for an empty record type. CSV is for inspection; JSONL remains the source for restoration. CSV fields containing JSON are serialized as JSON text, and formula-like cells are prefixed with an apostrophe for spreadsheet safety. The manifest records checksums and row counts for both CSV files; validation regenerates them from the JSONL records and checks they match. The validator continues to accept format v2 archives, which have no CSV files. ZIP contents may include personal information and require the same access controls as the original JSONL.

CSV rules, exactly (`_csv_cell`): a null is an empty cell; a timestamp is UTC ISO-8601; a nested value (JSON object or list) is its canonical JSON text; everything else is its text. A cell whose text, after any leading whitespace (Unicode included) or control characters, starts with `=`, `+`, `-`, `@` or `|`, or whose first character is a control character, is prefixed with `'` so a spreadsheet shows it as text — this also prefixes an honest negative number, which is why the CSV is never the restore source. Column order is the manifest's `columns`; line ends are `\n`; quoting is minimal; the bytes are deterministic. Validation rejects any CSV that is not byte-identical to what the JSONL records regenerate (row or header order, an edited cell, a dropped or appended row, an empty member), any manifest that misstates a CSV digest, size or row count, an extra member, and a manifest claiming v2 while CSV members are present. Objects of format v3 live under `…/v3/…` keys; no v2 object was ever written outside tests (nothing was deployed), so the version bump reuses nothing.

Restore: `product_analytics_archive.restore_archive_rows(db, payload)` validates the archive, inserts its JSONL records into the live tables with `INSERT … ON CONFLICT (event_id | engagement_id) DO NOTHING` (a record already present is left untouched; `id` is assigned anew; columns the archive omitted come back NULL), returns rows inserted per table and leaves the commit to the caller. Restored rows are age-expired again and are re-archived by the next run under a new key unless retention is disabled.
